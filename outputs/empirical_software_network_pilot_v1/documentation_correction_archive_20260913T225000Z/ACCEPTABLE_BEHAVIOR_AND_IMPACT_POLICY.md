# Acceptable Network Behavior and Software Impact Policy

## 1. Scope and Authority

This policy defines the normative boundaries for acceptable PTP timing traffic, operational thresholds for anomaly detection, and the criteria for identifying measurable software-level receiver impacts in the emulated O-RAN S-Plane network.

All definitions apply strictly to the software-emulated testbed under Linux network namespaces and software bridge devices.

---

## 2. Approved Timing Source Specification

Only traffic originating from authorized Grandmaster clocks conforming to the following parameters is considered an approved timing source:

| Parameter | Primary Master (Master A) | Secondary Master (Master B) | Notes |
|---|---|---|---|
| **PTP Domain** | 0 | 0 | Default IEEE 1588 / O-RAN domain |
| **Network Transport** | Layer 2 Ethernet (`0x88f7`) | Layer 2 Ethernet (`0x88f7`) | IEEE 802.3 multicast |
| **Priority 1** | 100 | 150 | Best Master Clock Algorithm (BMCA) selects Master A when both are healthy |
| **Clock Class** | 248 | 248 | Standard software default |
| **Delay Mechanism** | E2E (End-to-End) | E2E (End-to-End) | Software measurement |
| **Clock Stepping** | Disabled (`free_running 1`) | Disabled (`free_running 1`) | Prevents host clock modification |

## 3. Expected Message Rates and Baseline Tolerances

Under nominal operating conditions, timing traffic must satisfy the following message frequencies:

| Message Type | Log Interval | Nominal Period | Nominal Rate | Acceptable Rate Envelope |
|---|---|---|---|---|
| **Sync** | `-3` | $0.125\text{ s}$ ($125\text{ ms}$) | $8\text{ packets/s}$ | $6\text{ to }10\text{ packets/s}$ |
| **Follow_Up** | Matched to Sync | $0.125\text{ s}$ ($125\text{ ms}$) | $8\text{ packets/s}$ | One-to-one pairing with Sync |
| **Announce** | `-2` | $0.25\text{ s}$ ($250\text{ ms}$) | $4\text{ packets/s}$ | $3\text{ to }5\text{ packets/s}$ |
| **Delay_Req** | `-3` | $0.125\text{ s}$ ($125\text{ ms}$) | $8\text{ packets/s}$ | Generated by slave |

## 4. Anomaly Detection Threshold Table (Frozen)

The streaming discriminator applies the following frozen thresholds to incoming packet streams:

| Parameter | Value | Rationale |
|---|---|---|
| **Block Size ($B$)** | $8\text{ packets}$ | Corresponds to exactly $1.0\text{ second}$ of nominal Sync traffic ($8 \times 0.125\text{ s}$). |
| **Dispersion Threshold ($\sigma_{\text{thresh}}$)** | $0.00016\text{ s}$ ($160\ \mu\text{s}$) | Separates nominal queuing dispersion ($\sigma < 25\ \mu\text{s}$) from disruptive network jitter ($\sigma > 200\ \mu\text{s}$). |
| **Persistence Count ($K$)** | $2\text{ blocks}$ | Requires two consecutive non-overlapping blocks to exceed the dispersion threshold, preventing false alarms from isolated packet delays. |
| **Persistence Window ($W$)** | $3.0\text{ s}$ | High-dispersion blocks must occur within 3 seconds to confirm active, sustained impairment. |
| **Announce Timeout ($T_{\text{announce}}$)** | $0.75\text{ s}$ | Corresponds to 3 missed Announce intervals ($3 \times 0.25\text{ s}$), matching IEEE 1588 `announceReceiptTimeout 3`. |

## 5. Measurable Software-Level Impact Definitions

In this software emulation, impact is evaluated at the receiver daemon and Linux network stack level. The observable states are:

### 1. `ptp4l` Receiver Port States
- **`LISTENING`**: The port is passive and receiving Announce messages to evaluate master availability via BMCA.
- **`UNCALIBRATED`**: The port has selected a master and is synchronizing message sequences before transitioning to tracking.
- **`SLAVE`**: The port is actively tracking the chosen grandmaster.
- **`FAULTY`**: The port has experienced an interface link-down or fatal protocol error and has stopped processing traffic on that segment.

### 2. Standby Port Takeover
- A valid self-healing failover requires:
  1. The primary port (Segment 1) transitioning from `UNCALIBRATED` or `SLAVE` to `FAULTY`.
  2. The standby port (Segment 2) transitioning from `LISTENING` to `UNCALIBRATED` following the primary port fault.
  3. Corroborated cessation of egress traffic on the Segment 1 bridge interface.

### 3. Traffic Flow Continuity and Collapse
- When Segment 1 is shut down, egress packet counts reported by kernel queue disciplines (`tc -s qdisc show dev <veth>`) must cease increasing on Segment 1, while packet flow continues or commences on Segment 2.

## 6. Explicit Non-Claims

1. **Shared Host Monotonic Clock:**
   The host running the Linux emulation provides the single underlying timebase for all network namespaces. Disabling clock discipline via `free_running 1` ensures that no process alters the host clock. Consequently, relative clock offset between master and slave namespaces reflects internal scheduling latency rather than physical oscillator drift.

2. **No Hardware Physical Layer Conformance:**
   The measurements do not establish compliance with physical telecom boundaries (such as ITU-T G.8273.2 Class C $\pm 30\text{ ns}$ or Class D $\pm 5\text{ ns}$ Time Error limits). Physical validation requires dedicated hardware test equipment (e.g., Calnex Paragon-Neo) and hardware timestamping NICs.
