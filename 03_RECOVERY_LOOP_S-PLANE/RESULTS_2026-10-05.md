# Recovery loop — results, 5 Oct 2026

**140 live runs**: 14 scenarios × 2 arms × 5 replicates (13–17), on real linuxptp 4.0 daemons in the frozen G.8275.1 software testbed.
- **Pre-registration:** written and SHA-256 frozen before the first evaluation run (`code/FROZEN_RL.json`). The freeze was re-verified before every run and again after the last one.
- **Scoring:** outcomes come only from the passive pmc observer, which is identical in both arms.
- **Independent check:** a separate scoring pass rewrote the scoring from the definitions and reproduced every outcome (see §5).

## 1. Headline

| | Control (detect only, no action) | Closed loop |
|---|---|---|
| A1 rogue grandmaster: RU1/RU2 following the rogue | 38.5 s of 40 (5/5 never recovered) | **2.0 s** median (restored 5/5) |
| C1 interception (BC port blackholed, never restored): RU1/RU2 without a master | 39.0 s of 40 (5/5 never recovered) | **2.5 s** median (restored 5/5, via standby BC) |
| C3 whole-second abuse: RU1/RU2 following the forger | 38.5 s of 40 (5/5 never recovered) | **2.0 s** median (restored 5/5) |
| A2, A3, A5, A8, C2: RU1/RU2 impact | 0 s (no measurable impact) | 0 s; attacker's ingress port isolated and verified in 5/5 each |
| Benign / healthy (baseline, B2, B3, B7, B_bc_replacement) | — | 1 disruptive action in 25 runs (B3 r17; see §3) |
| Ambiguous (B_unplanned_failover) | — | 0 actions; escalated 5/5 |

**Timing:** detection about 1.1 s after the fault, action about 2.1 s after it, verification of the restored parent and grandmaster within about 1 s.

## 2. Pre-registered hypotheses

| Hypothesis | Result | Detail |
|---|---|---|
| **H1 restoration** | **PASS** | Loop restored 5/5 in all 8 attack scenarios; loop median ≤ control median in all 8; where the control median was ≥ 5 s (A1, C1, C3) the loop median was ≤ 6.5 % of it |
| **H2 containment** | **PASS** | ISOLATE executed and verified 5/5 in A1, A2, A3, A5, A8, C2, C3; standby failover executed and verified 5/5 in C1 |
| **H3 no harm on benign** | **FAIL** | 1 disruptive action in 25 benign loop runs (Wilson 95 % [0.007, 0.195]) |
| **H4 honest abstention** | **PASS** | B_unplanned_failover: 0 actions, escalation 5/5 |
| **Control integrity** | **PASS** | 0 executed actions in 70 control runs (41 `would_act` logged); confirmed from artefacts: no nft `rl` table and no standby daemon in any control run |

H1 passes **trivially** for A2, A3, A5, A8 and C2. In those five, the attack did not degrade RU1/RU2 at all in the control arm. For them the loop shows *containment* (H2), not a restoration benefit.

## 3. The H3 failure, explained, not excused

In B3_pdv_congestion replicate 17, the run was not the intended mild congestion:
- **Apparatus:** the background-traffic generator hit `ENOBUFS` in both arms.
- **BC fault:** the boundary clock hit `timed out while polling for tx timestamp`, and its downstream port went `MASTER → FAULTY` for about 16 s.
- **Control arm:** RU1/RU2 really lost timing (LISTENING) for **16.5 s**.
- **Loop arm:** the service-continuity channel saw no Announce for more than 2 s and activated the standby BC at T0 + 5.1 s. Verification passed, and RU1/RU2 were unhealthy for **3.5 s**.

So the action responded to a genuine outage and shortened it. It is still a disruptive action in a scenario labelled benign, and the pre-registered criterion counts it as a failure. The loop's service-loss trigger acts on *consequence*, not intent. A benign fault severe enough to remove timing will trigger failover, and this is by design (RFC 7384 §5.9 redundancy). The pre-registration did not anticipate a benign run turning into a real outage, which is why the criterion was written as zero actions.

## 5. Independent verification

A separate pass rewrote the scoring from the pre-registration (it did not import `analyse.py` or `report.py`). It reproduced every hypothesis verdict and every loop-arm value, restoration count, action, target and verification count. It also cross-checked actions against artefacts with **0 mismatches**:
- 35/35 isolations present in the final nft ruleset;
- 6/6 standby activations with a `bcs.log`;
- no `rl` table or `bcs.log` in any control run.

**One disagreement:** for the 15 control runs of A1, C1 and C3, the project scorer stops at the last observer sample (about T0 + 39.55 s) instead of T0 + 40 s. This under-counts control-arm harm by about 0.44 s per run (for example 38.51 vs 38.96 s). The error favours the control, and no verdict changes.

## 6. Limits

- **Clock steering:** `free_running 1` is kept, so the outcome is *who the RUs follow*. Nanosecond time error is not measured.
- **Collateral on RU3:** where the injector shares RU3's port (A2, A3, A5, C2, C3), isolation also stops RU3's own Delay_Req. In C3, RU3 kept following the forger for the whole run (38.5 s), because the injector sits in RU3's own namespace.
- **Isolation mechanism:** an nftables bridge filter stands in for a switch-port PTP filter. It is not IEEE 1588 Annex P authentication (linuxptp 4.0 has none).
- **Inherited detector limits:** the loop inherits the detector's limits. The base rule's false A8 on a provisioned BC still fires; the safety guard prevents any action and escalates once.
- **Small sample:** 5 replicates per arm per scenario; intervals are wide.
- **No digital twin:** actions are verified after execution, not rehearsed.
